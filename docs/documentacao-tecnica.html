Documentação técnica de arquitetura

Sistema de Gestão — Clínica Noely Cerqueira

Node.js / Express / Prisma API Vue 3 / Vite site e painel PostgreSQL banco de dados Multi-tenant ready — hoje 1 tenant em produção

Este documento descreve como o sistema é construído por dentro — arquitetura, modelo de dados, módulos, autenticação e decisões técnicas notáveis — para qualquer desenvolvedor que precise dar manutenção ou continuar o projeto sem ter acompanhado sua construção.

O sistema tem duas metades independentes que só se falam por HTTP/JSON: uma API (server/) que concentra toda regra de negócio e acesso ao banco, e um site (web/) que é uma SPA (Single Page Application) consumindo essa API — tanto para o site público de agendamento quanto para o painel administrativo interno.

01

Arquitetura da solução

Em produção, cada peça vive num provedor diferente, escolhidos por custo-benefício (detalhes de contas e variáveis em DEPLOY.md). A API nunca escreve em disco de forma persistente — tanto o banco quanto os arquivos de upload ficam em serviços gerenciados externos, porque a hospedagem da API (Railway) tem disco efêmero: qualquer arquivo local desaparece a cada novo deploy.

Por que separar site e API assim

Desacopla o custo e o ciclo de deploy de cada metade — um pico de acesso ao site (CDN da Netlify, praticamente grátis) não pressiona o mesmo processo que roda a lógica de negócio, e vice-versa. Também é o motivo do banco (Neon) e do storage (Supabase) serem serviços gerenciados externos: Railway não garante disco persistente entre deploys.

03

Modelo de dados

Toda tabela relevante carrega tenantId: o isolamento entre clínicas é sempre um filtro explícito nas consultas, nunca implícito — o schema já está pronto para múltiplos tenants, mesmo que hoje exista apenas um (noely-cerqueira) em produção.

Decisão notável

PatientFicha.fields é um Json livre (lista de {"{"}label, value{"}"}), não colunas fixas — os tipos de ficha clínica (um por procedimento/protocolo) crescem com o tempo, e cadastrar um tipo novo não pode depender de uma migração de banco. Uma ficha pode ser preenchida campo a campo, ou ser só um upload de arquivo digitalizado (fileStorageKey), ou as duas formas juntas.

05

Autenticação e autorização

Sem sessão em servidor: o login emite um JWT (válido 8h) que carrega id, papel e tenant do usuário. Toda rota protegida decodifica esse token via middleware antes de tocar em qualquer regra de negócio.

Caso especial

requireAuthFromHeaderOrQuery existe porque uma tag <img src> ou <a target="_blank"> do navegador não envia o cabeçalho Authorization — usado nas duas rotas que servem arquivo direto (foto de paciente, arquivo de ficha), aceitando o token também via query string da própria URL.

06

Multi-tenancy

Todo request passa por resolveTenant antes de qualquer rota de negócio: ele lê o header x-tenant-slug (ou usa noely-cerqueira como padrão, já que hoje só existe um tenant) e carrega o registro correspondente, disponibilizando-o como req.tenant para o resto da cadeia.

Isso significa que nenhuma query do sistema assume um id fixo de clínica — toda consulta ao Prisma filtra por tenantId explicitamente. Adicionar uma segunda clínica no futuro não exige tocar em nenhuma rota existente, só em como o slug é resolvido (hoje fixo, poderia virar subdomínio ou header vindo de um proxy).

07

Concorrência na agenda

Impedir dois agendamentos sobrepostos não pode depender só de "checar antes de inserir" na aplicação — sob concorrência real (duas pessoas confirmando o mesmo horário quase ao mesmo tempo), essa checagem tem uma janela de corrida. A garantia definitiva vive no próprio banco: uma EXCLUDE CONSTRAINT via btree_gist (SQL manual, fora do fluxo normal de migrations do Prisma — ver prisma/manual-sql/001_appointment_no_overlap.sql) rejeita, a nível de banco, qualquer inserção cujo intervalo [startAt, endAt) sobreponha outro agendamento confirmado do mesmo tenant.

08

Armazenamento de arquivo

Fotos de paciente e fichas digitalizadas nunca ficam em diretório público estático — são dado sensível (LGPD), sempre servidas por rota autenticada que busca o arquivo sob demanda. lib/file-storage.ts abstrai duas implementações atrás da mesma storageKey (um caminho relativo, nunca absoluto):

  • Disco local (padrão, sem variáveis configuradas) — usado em desenvolvimento, em server/uploads/.
  • Storage S3-compatível (quando S3_ENDPOINT está definido) — obrigatório em produção, já que o disco do Railway é efêmero. O client (@aws-sdk/client-s3) e o endpoint/região são genéricos de propósito: atende Supabase Storage (provedor em uso hoje), Cloudflare R2 ou qualquer outro compatível com a API S3, sem alterar uma linha de código — só variáveis de ambiente.
09

Auditoria e LGPD

Duas camadas de rastreabilidade coexistem:

  • Escrita — auditLogger (middleware transversal) grava toda ação CREATE/UPDATE/DELETE feita por um usuário autenticado do painel: quem, o quê, quando, e o corpo da requisição com campos sensíveis (senha etc.) removidos antes de salvar.
  • Leitura de dado sensível — abrir a ficha de um paciente ou suas fichas clínicas gera um registro próprio de ação VIEW, único caso em todo o sistema onde uma simples consulta (GET) é auditada. Reflete a exigência da LGPD de rastrear quem acessou um dado pessoal sensível, não só quem o alterou.

Controle de acesso por papel reforça a mesma lógica: RECEPTION nunca vê notas clínicas nem a galeria de fotos de um paciente (só o essencial para atender/agendar), e fichas clínicas completas exigem ADMIN em toda rota, sem exceção.

10

Frontend

Vue 3 com Composition API, roteado por Vue Router e com estado de sessão em Pinia. Duas áreas dentro do mesmo build:

  • Site público (/, /servicos, /agendar, /contato) — vitrine institucional com animações GSAP/ScrollSmoother, consumindo catalog, availability, settings e criando agendamentos.
  • Painel administrativo (/admin/*) — protegido por login, telas de agenda, pacientes, financeiro, estoque, catálogo (gestão), usuários e auditoria, uma por módulo da API.

Build único via Vite (npm run build → dist/), servido como site estático — todo roteamento de rota profunda (ex. recarregar /admin/pacientes direto) depende do redirect SPA configurado no host (web/netlify.toml).
