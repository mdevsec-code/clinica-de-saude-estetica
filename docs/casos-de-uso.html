Especificação de casos de uso

Sistema de Gestão — Clínica Noely Cerqueira

55 casos de uso 4 atores 13 pacotes funcionais Base: rotas e regras implementadas no código (server/src/modules)

Este documento especifica, em formato UML, todos os casos de uso do sistema que sustenta a operação da Clínica Noely Cerqueira (Camaçari, BA): agendamento público, agenda interna, prontuário de pacientes, financeiro, estoque e administração de acesso. Cada caso de uso reflete uma rota e uma regra de negócio de fato implementadas — nenhum item aqui descreve uma intenção futura.

Quatro atores interagem com o sistema: o Visitante do site público (sem login), a Recepção e o Administrador — os dois papéis de acesso ao painel interno (RECEPTION e ADMIN) — e o Sistema, que executa dois processos automáticos sem intervenção humana direta (geração de retorno e registro de auditoria).

PACOTE 01

Site público

VISITANTE

Nenhuma autenticação envolvida. É a porta de entrada do cliente final — consulta o catálogo, vê horários livres e agenda, tudo sem criar conta.

UC01

Consultar catálogo de serviços

GET /catalog/categories
Pré-condição
Nenhuma.
Pós-condição
Visitante visualiza categorias ativas com seus serviços ativos, preços e durações.
Fluxo principal
  1. Visitante abre a página de serviços.
  2. Sistema busca categorias e serviços ativos do tenant.
  3. Sistema retorna a lista, já ordenada por destaque/ordem cadastrada.
UC02

Consultar horários disponíveis

GET /availability/slots
Pré-condição
Visitante já escolheu um serviço e uma data.
Pós-condição
Sistema apresenta os horários livres daquele dia para aquele serviço.
Fluxo principal
  1. Visitante informa serviceId e date.
  2. Sistema cruza horário de funcionamento, duração do serviço, agendamentos já confirmados e bloqueios do dia.
  3. Sistema retorna os horários vagos, na granularidade configurada (15 min por padrão).
Exceção
Data fora da janela de antecedência mínima/máxima configurada — lista vem vazia.
UC03

Consultar dados de contato e funcionamento

GET /settings/public
Pré-condição
Nenhuma.
Pós-condição
Visitante vê WhatsApp, Instagram, e-mail, endereço e horário de funcionamento da clínica.
Fluxo principal
  1. Página pública solicita as configurações do tenant.
  2. Sistema retorna os dados de contato e os dias/horários ativos.
UC04

Agendar atendimento

POST /appointments
Pré-condição
Visitante escolheu serviço e horário disponível (UC02).
Pós-condição
Agendamento criado com status CONFIRMED, origem PUBLIC_SITE; cliente é criado ou reaproveitado por WhatsApp.
Fluxo principal
  1. Visitante informa nome, WhatsApp (e opcionalmente e-mail), serviço e horário.
  2. Sistema localiza cliente existente pelo WhatsApp ou cria um novo.
  3. Sistema tenta reservar o intervalo — uma exclude constraint no banco impede sobreposição mesmo sob concorrência (dois visitantes clicando "confirmar" ao mesmo tempo).
  4. Sistema confirma o agendamento e retorna os dados.
Exceção
Horário foi tomado por outra reserva no instante da confirmação → sistema rejeita com erro de conflito, sem duplicar o horário. Limite de tentativas por IP (rate limit) protege contra abuso automatizado.
PACOTE 02

Autenticação

RECEPÇÃOADMIN
UC05

Autenticar-se no painel

POST /auth/login
Pré-condição
Usuário possui conta ativa no tenant.
Pós-condição
Usuário recebe um token JWT (validade 8h) que autoriza as próximas requisições.
Fluxo principal
  1. Usuário informa e-mail e senha.
  2. Sistema localiza a conta pelo par tenant+e-mail e confere o hash da senha.
  3. Sistema emite o token com id, papel (ADMIN/RECEPTION) e tenant embutidos.
Exceção
Conta inexistente, senha incorreta ou conta desativada → mesma mensagem genérica de erro nos três casos, para não revelar quais e-mails existem no sistema. Limite de tentativas por rota (rate limit) contra força bruta.
UC06

Consultar sessão atual

GET /auth/me
Pré-condição
Token válido no cabeçalho da requisição.
Pós-condição
Painel confirma quem está logado e com qual papel, para decidir o que exibir na interface.
Fluxo principal
  1. Painel consulta a rota ao carregar.
  2. Sistema devolve os dados do usuário decodificados do próprio token.

Exceção
Credenciais da WhatsApp Cloud API não configuradas → erro claro em vez de falha silenciosa.

Nenhuma.
Pós-condição

UC36

Gerar DRE do período

GET /finance/dre
Pré-condição
Usuário informa data inicial e final.
Pós-condição
Demonstração de Resultado simplificada: Receita Bruta (atendimentos concluídos) − Despesas por categoria (gastos pagos) = Resultado Líquido, com margem percentual.
Fluxo principal
  1. Usuário define o período.
  2. Sistema soma receita e despesas pagas agrupadas por categoria naquele intervalo.
  3. Sistema calcula resultado líquido e margem.
Exceção
Regime de caixa, não de competência — e sem linha de impostos/CMV, porque o sistema não rastreia esse dado ainda.
UC37

Importar extrato bancário (OFX)

POST /finance/bank/import ADMIN
Pré-condição
Admin possui um arquivo de extrato no formato OFX.
Pós-condição
Transações do extrato importadas como UNMATCHED, prontas para conciliar.
Fluxo principal
  1. Admin envia o conteúdo do OFX.
  2. Sistema identifica cada transação pelo FITID (identificador único do próprio banco).
  3. Sistema grava só as transações ainda não importadas.
Exceção
Reimportar o mesmo extrato (ou período sobreposto) nunca duplica lançamentos — o FITID já existente é simplesmente ignorado.
UC38

Consultar transações bancárias

GET /finance/bank/transactions
Pré-condição
Nenhuma.
Pós-condição
Lista de transações importadas, filtrável por status de conciliação.
Fluxo principal
  1. Usuário abre a tela de conciliação.
  2. Sistema retorna as transações e o gasto já vinculado, quando houver.
UC39

Consultar sugestões de conciliação

GET /finance/bank/transactions/:id/suggestions
Pré-condição
Transação é de saída (débito).
Pós-condição
Até 5 gastos candidatos, com o mesmo valor e data próxima (±5 dias), ainda não conciliados.
Fluxo principal
  1. Usuário pede sugestões para uma transação.
  2. Sistema busca gastos compatíveis por valor exato e janela de data.
UC40

Conciliar transação bancária

POST /finance/bank/transactions/:id/match ADMIN
Pré-condição
Transação e gasto existem.
Pós-condição
Transação marcada MATCHED; se o gasto ainda estava PENDING, é automaticamente dado como pago na data em que o banco processou.
Fluxo principal
  1. Admin escolhe o gasto correspondente (de uma sugestão ou manualmente).
  2. Sistema vincula os dois e dá baixa no gasto, se necessário, numa única operação.
UC41

Desfazer conciliação

POST /finance/bank/transactions/:id/unmatch ADMIN
Pré-condição
Transação está conciliada.
Pós-condição
Transação volta a UNMATCHED; o vínculo com o gasto é removido (o gasto em si não é alterado).
Fluxo principal
  1. Admin identifica uma conciliação incorreta.
  2. Sistema desfaz o vínculo.
UC42

Ignorar transação bancária

POST /finance/bank/transactions/:id/ignore ADMIN
Pré-condição
Transação existe.
Pós-condição
Transação marcada IGNORED (ex.: transferência pessoal, sem relação com a clínica) — sai da fila de conciliação pendente.
Fluxo principal
  1. Admin identifica uma transação sem gasto correspondente.
  2. Sistema marca como ignorada.

Nova senha definida; Admin repassa o valor à pessoa por um canal seguro.

Auditoria

ADMIN

UC53

Consultar log de auditoria

GET /audit
Pré-condição
Nenhuma.
Pós-condição
Histórico paginado de ações, filtrável por usuário, tipo de entidade, ação e período.

PACOTE 13

Processos automáticos

SISTEMA

Nenhuma pessoa aciona estes dois casos de uso diretamente — o Sistema os executa como consequência de outra ação.

UC54

Gerar procedimento e lembretes de retorno

sub-fluxo de UC08
Pré-condição
Um agendamento foi marcado como COMPLETED.
Pós-condição
Um ProcedureRecord é criado (histórico do procedimento realizado) e, se o serviço tiver dias de retorno configurados (ex.: Botox = 15 e 122 dias), um ReturnReminder é criado para cada um, com data já calculada e congelada.
Fluxo principal
  1. Sistema detecta a mudança de status para concluído.
  2. Sistema cria o registro de procedimento vinculado ao agendamento.
  3. Sistema lê Service.returnOffsetDays e cria um lembrete por dia configurado.
UC55

Registrar log de auditoria a cada escrita

middleware transversal
Pré-condição
Uma requisição autenticada de escrita (POST/PATCH/PUT/DELETE) chega a qualquer rota do painel.
Pós-condição
Um registro de auditoria é gravado com usuário, ação, entidade afetada e corpo da requisição (com senhas e outros campos sensíveis removidos antes de salvar).
Fluxo principal
  1. Sistema intercepta a requisição antes dela chegar à rota de negócio.
  2. Sistema aguarda a resposta ser enviada (res.on('finish')).
  3. Sistema grava o log de forma assíncrona, sem atrasar a resposta ao usuário.
Exceção
Agendamento público (UC04) nunca passa por aqui — não há usuário autenticado nessa rota.
